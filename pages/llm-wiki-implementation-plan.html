LLM Wiki · Implementation Plan

Building an LLM Wiki for your project, from scratch

A concise plan anyone can follow: what you need before you start, which building blocks to assemble, how they work together, and the six phases that take you from an empty folder to a self-maintaining project knowledge base.

1 · The big picture

One sentence: team members drop any document into a shared folder, and an AI automatically turns it into organized, searchable wiki pages — with a full audit trail.

Drop zone

A shared OneDrive folder. Anyone drops meeting notes, specs, transcripts, photos.

→

Courier

Power Automate notices the new file and delivers it to the vault.

→

Vault

A GitHub repository — the wiki's permanent, version-controlled home.

→

Librarian

GitHub Actions wakes a script that asks the AI to read the file and write wiki pages.

→

Reading room

The team browses and searches the wiki in Obsidian (or on GitHub itself).

Every piece is a standard, off-the-shelf service — nothing custom-built except one Python script (the librarian's brain-stem) and one rulebook file (the constitution). That's what makes this buildable in about two weeks.

2 · What you need before you start

Four accounts, two people, one decision workshop.

Obsidian Free desktop app for reading and lightly editing the wiki. Optional — the wiki is readable on GitHub in any browser — but Obsidian makes the page links clickable and pretty. Free
One technical person Someone comfortable with Python and GitHub for the two-week setup. After setup, no ongoing technical skill is needed for daily use. ~2 weeks, once
One named curator A team member who owns quality: reviews AI-written pages, merges duplicates, and keeps the rulebook honest. Roughly 30 minutes a week. 30 min/week
A decision workshop Half a day with the team to decide what the wiki is for, what its sections are, and what the naming rules should be. Do this before building anything — it becomes the constitution. Half a day

3 · The tech stack

Seven components. Five are services you configure; two are things you write.

Component What it is Its job in the system
OneDrive Cloud file storage (Microsoft 365) The drop zone — one shared folder where the team drops raw documents. No formatting, no rules, just drop.
Power Automate Microsoft's point-and-click automation tool The courier — a small "flow" that watches the drop-zone folder and, when a file appears, copies it into the GitHub repository's inbox folder via the GitHub connector.
GitHub repository Version-controlled file storage The vault — holds the wiki pages, the inbox, the archive, and the rulebook. Every change ever made is preserved, so nothing can be lost or silently overwritten.
GitHub Actions GitHub's built-in automation runner The alarm bell — a small instruction file that triggers the librarian whenever a new file lands in the inbox, plus a weekly safety sweep for anything missed.
Python script ~800 lines of code you write once The librarian — extracts text from any format (Word, PDF, PowerPoint, Excel, transcripts, images), checks for duplicates, sends the content to the AI with the rulebook, writes the resulting pages, and logs everything.
Claude API Anthropic's AI, called over the internet The brain — reads each document and decides what's worth keeping: decisions, lessons, who owns what. Writes or updates wiki pages following the constitution.
Constitution file One markdown document (CLAUDE.md) The rulebook — defines the wiki's sections, naming rules, quality bar, and what counts as knowledge worth keeping. This is where your workshop decisions live, and it's what keeps the AI's output consistent.

4 · How the pieces work in unison

Follow one document through the system.

1

A consultant drops "Design Review Notes.docx" into the OneDrive folder

That's the entire human effort. No template, no tagging, no form to fill in.

2

Power Automate delivers it to GitHub within a minute

The flow authenticates to GitHub, places the file in the repository's raw/inbox/ folder, and commits it. That commit is the trigger.

3

GitHub Actions wakes the librarian script

The script converts the Word file to text, confirms it hasn't been seen before, and sends the text to Claude — together with the constitution, the current page catalog, and the full content of existing pages so the AI updates rather than duplicates.

4

The AI files the knowledge

It might update the project overview, create a decision page with the rationale, add two questions to the open-questions list, and record a hard-won lesson. Every AI-written page is tagged as machine-generated until a human validates it.

5

Everything is recorded, then saved back

The catalog is updated, a diary entry says exactly what changed and why, the original document moves to the permanent archive, and GitHub Actions commits it all. Minutes after the drop, the team can read the new pages in Obsidian or the browser.

Why this architecture is safe

Three properties protect you: nothing is deleted (originals are archived, pages are marked outdated rather than removed), everything is versioned (GitHub keeps every historical state, so any mistake can be undone), and every AI action is logged (the diary shows what was read and what was written, so trust is verifiable, not assumed).

5 · Implementation plan — six phases

Realistic total: about two calendar weeks of setup, then a four-week pilot.

0

Half a day · whole team

Decide before you build

  • Run the decision workshop: what is this wiki for, who reads it, what are its sections?
  • Interview the team on how they'd use it (use a discovery questionnaire).
  • Write the outcomes into the constitution file — sections, naming rules, quality bar.
1

1–2 days · technical person

Build the vault skeleton

  • Create a private GitHub repository.
  • Create the folder structure: the content sections, raw/inbox/, raw/processed/, and meta/ (catalog, diary, duplicate-checklist, name dictionary).
  • Add a page template inside each folder so humans and the AI see the expected format.
  • Commit the constitution file at the root.
2

3–5 days · technical person

Build the librarian

  • Write the Python ingestion script: text extraction for each file type, duplicate check, the AI prompt (embedding the constitution), page writing, catalog/diary updates.
  • Create the GitHub Actions workflow: trigger on inbox changes + weekly sweep + manual button.
  • Store the Anthropic API key as a GitHub secret — never in the code.
  • Build in the safety rails: retries on network hiccups, failed files stay in the inbox for retry, unreadable files get logged for the curator.
  • Test with a handful of real documents of each type.
3

Half a day · technical person

Build the bridge

  • Create the shared OneDrive folder and give the team access.
  • Build the Power Automate flow: trigger "when a file is created" on that folder, action "create/update file" in the GitHub repository via the GitHub connector.
  • Test end-to-end: drop a file in OneDrive, watch pages appear in the wiki.
4

Half a day · everyone

Open the reading room

  • Install Obsidian for team members who want it; point it at a synced copy of the repository.
  • Everyone else reads via the GitHub web interface — no install needed.
  • Agree the correction path: who fixes a wrong page, and how.
5

1 week · curator + team

Seed it

  • Back-ingest the twenty most valuable existing documents — old specs, decision records, the defect log. An empty wiki wins no converts.
  • Curator reviews the AI-generated pages: validate the good, correct the wrong.
  • Pick one flagship use case to nail first (e.g. "explain our legacy code" or "answer new-joiner questions").
6

4 weeks · whole team

Pilot, then make it a habit

  • Run a four-week pilot with one project/workstream. Every meeting's notes get dropped.
  • Weekly 20-minute review: what failed to ingest, what needs correcting, what repeated this week that deserves a permanent page?
  • Measure the signal the team chose (fewer repeated questions, faster onboarding, wiki links appearing in tickets) — then decide to expand or adjust.

The three things that decide success

  • The drop habit. The technology works from day one; adoption doesn't. Make dropping files someone's named responsibility per meeting until it's reflex.
  • Trust through honesty. Keep AI-written pages visibly tagged until a human validates them. One confidently-wrong page hurts more than ten missing ones.
  • The curator role. Thirty minutes a week of human curation is the difference between a compounding knowledge base and an abandoned folder of robot notes.
