ABAP LLM Wiki · Team Discovery

Fifty-six questions before we build the habit

A workshop kit for interviewing the ABAP team about the AI-powered knowledge vault. Part 1 (A–I) finds out what the wiki should contain. Part 2 (J–N) finds out how it must behave to actually get used.

Why these questions

Industry research on SAP teams says the problem is real: a typical ECC system carries ~22,000 custom objects whose original authors have moved on, documentation is the most-cited gap in custom code management, and custom code that "nobody fully understands anymore" is the single biggest cause of S/4HANA migration overruns. So the interview isn't about whether a knowledge vault helps — it's about finding which specific losses hurt this team, so the wiki earns daily use instead of becoming another shelf nobody visits.

Amber-marked questions form the 30-minute shortlist — ask these if time is short.

Part 1 — What should the wiki contain?

Themes A–I: knowledge losses, repeat demand, source material, legacy code, trust, and success criteria.

A

Where your knowledge lives today

Goal: map the current, informal system — the vault has to beat it, not just exist alongside it.

  1. 1When you need to understand a custom program you didn't write, what do you do first — read the code, ask a colleague, search old emails, check a shared drive?
  2. 2Think of the last time you spent more than half a day figuring something out that a teammate already knew. What was it, and why didn't their knowledge reach you?
  3. 3Which person on the team, if they left tomorrow, would take the most irreplaceable knowledge with them? What do they know that's written down nowhere?
  4. 4Where do design decisions get recorded today — and have you ever discovered two conflicting "decisions" on the same topic?
  5. 5What documentation do you actually trust today, and why? What documentation exists but you've stopped reading?
B

The questions you answer over and over

Goal: seed the FAQ and troubleshooting sections with real repeat demand.

  1. 6What are the three questions new joiners or functional consultants ask you most often?
  2. 7Which recurring production problems (failed IDocs, stuck background jobs, authorization errors, interface failures) do you re-diagnose from scratch every time? Is there a diagnostic path you keep re-walking?
  3. 8What do clients or the functional team repeatedly ask that you wish had a standing, written answer?
  4. 9Which "gotchas" — non-obvious SAP behavior that cost you hours — have bitten more than one person on this team?Ask for specific stories: a COMMIT flag, a lock behavior, a transport ordering surprise.
C

What to feed the librarian

Goal: decide which document types the pipeline should prioritize, and remove friction from the drop-zone habit.

  1. 10What artifacts does your work actually produce — meeting notes, FS/TS documents, transcripts, emails, chat threads, spreadsheets, WRICEF lists? Which of these contain knowledge that dies today?
  2. 11Would you realistically drop a raw meeting transcript or an email thread into a folder, if that's all it took? What would stop you?Confidentiality, effort, habit, tooling?
  3. 12Are there existing document troves worth back-ingesting — old design documents, a SharePoint of specs, a defect log from the last go-live?
D

Legacy code — what the AI should reconstruct

Goal: prioritize the code-ingestion feature — the highest-value and hardest problem in the research.

  1. 13Which custom objects scare you the most to touch — and is that because of missing documentation, missing test data, or missing understanding of who uses them?
  2. 14If an AI drafted a functional spec for a legacy program (what it does in business terms, its dependencies, which processes break if it fails), what would that draft need to contain for you to bother reading it?
  3. 15Which matters more to document first: the objects changed most often, the objects that fail most often, or the objects in scope for migration/remediation?
  4. 16What dependency information do you look up repeatedly — where-used lists, table usage, which enhancement calls what?
E

Trust — the make-or-break for an LLM wiki

Goal: AI-generated pages carry a draft/ai-generated tag until a human validates them. Calibrate how the team wants that to work.

  1. 17How would you want AI-written pages marked so you always know what's machine-inferred versus human-confirmed?
  2. 18Who should validate AI-generated documentation, and how much review time per week is realistic — honestly?
  3. 19What's worse for you: a page that's missing, or a page that's confidently wrong? Can you give an example of documentation that misled you?
  4. 20If the AI gets something wrong and you spot it, what's the easiest correction path you'd actually use — edit the page, comment, tell one named person?
F

How you want to ask and consume

Goal: shape query mode and delivery — a wiki nobody opens is a failure regardless of content quality.

  1. 21When you have a question mid-task, where are you — in Eclipse/ADT, SAP GUI, Teams, a browser? Where would the answer need to appear to be useful?
  2. 22Would you rather browse pages, or ask questions in plain language and get an answer with sources cited? Or both?
  3. 23What answer format helps most: a direct answer with a link, a checklist, a code snippet, a "who to ask"?
  4. 24Should the wiki answer in English only, or do team members prefer another language for reading?
G

Estimates, actuals, and the numbers

Goal: the vault tracks estimated vs. actual effort per development — a calibration loop. Test appetite.

  1. 25How do you estimate WRICEF effort today, and do you ever look back at what a similar object actually took last time?
  2. 26Would you record actual effort on completed developments if it took under a minute — and what would make that feel worth it rather than surveillance?
H

Handovers and onboarding

Goal: test the vault's handover-readiness checklist against real handover pain.

  1. 27Describe the last handover you gave or received. What was missing? What did the leaver never write down?
  2. 28If a new developer joined your workstream Monday, what should they be able to find without asking anyone — day one, week one, month one?
I

Success criteria and anti-goals

Goal: get their definition of success — and their fears — on record before you build habits around the tool.

  1. 29Six months from now, what would make you say "the wiki saved me real time this week"? What's the first search you'd genuinely run?
  2. 30What would make you abandon it?Stale pages, wrong answers, duplicate pages, too much ceremony to contribute?
  3. 31Is there anything you would not want captured in a shared vault — client-sensitive material, half-formed opinions from meetings, individual performance signals?

Part 2 — How will the team actually use it?

Themes J–N: moments of use, personas, contribution habits, toolchain fit, and the first ninety days.

J

Moments of use — when would you open it?

Goal: identify the real triggers. A tool gets adopted when it attaches to moments that already exist in the workday.

  1. 32Walk me through yesterday. At which points in your day did you need information you didn't have in your head — and what did you do in each of those moments?
  2. 33What are you usually in the middle of when a knowledge question comes up: writing code, debugging a production issue, sitting in a meeting, estimating, reviewing a transport, writing a spec?
  3. 34In those moments, how much time will you realistically give the wiki before you give up and ping a colleague — thirty seconds? Two minutes?
  4. 35Are there scheduled moments where the wiki could have a standing role — sprint planning, defect triage, design reviews, the weekly team call, pre-transport-release checks?
  5. 36Would you use it before starting a new development (to check for prior decisions, similar objects, applicable standards), or does that check not happen today at all?
K

Who uses it, and differently

Goal: a senior developer, a new joiner, a functional consultant, and a project lead need different things from the same vault — find out which personas matter most.

  1. 37Who do you expect to be the heaviest readers of the wiki — developers, functional consultants, team leads, the client? And who will rarely touch it?
  2. 38Should functional consultants and the client see everything, or are there pages that should stay team-internal (rough estimates, candid meeting extracts, internal concerns)?
  3. 39Is there a role that mostly asks and a role that mostly answers today?The answer tells you whose time the wiki should save first.
  4. 40For project leads specifically: what would you want to pull from the wiki for status reporting, steering meetings, or audits — and would that change what gets captured?
L

Reading vs. contributing — the two-way street

Goal: everyone says yes to reading; adoption dies on contribution. Probe the contribution side hard.

  1. 41Be honest: after a meeting you ran, will you drop the notes into the inbox folder? Every time, sometimes, never? What would make it "every time"?
  2. 42Who should own dropping meeting material — the meeting organizer, a rotating role, whoever took notes?
  3. 43When you solve a nasty problem at 6pm, what's the maximum effort you'd spend capturing it — dropping a raw chat transcript, dictating two sentences, writing a proper note, or nothing?
  4. 44Would automatic capture from existing channels help — Teams meeting transcripts flowing in automatically, or a designated email address/channel that feeds the inbox — so contribution requires no extra step at all?
  5. 45When you correct something during a conversation ("no, we changed that decision in March"), should that correction flow into the wiki, and how would you want that to happen without breaking your conversation?
M

Fit with your actual toolchain

Goal: locate the wiki inside the tools they already live in, and find the friction points early.

  1. 46Which tools are open on your screen all day — Eclipse/ADT, SAP GUI, Teams, Outlook, browser, Excel, a ticketing tool (Jira/Solution Manager/ServiceNow)?
  2. 47Does the team already use Obsidian, or would reading happen via GitHub, a browser, or something else? Who would need help setting up access?
  3. 48When a defect ticket comes in, where does its story live today — and should the wiki link to tickets, mirror them, or stay out of ticket-land entirely?
  4. 49Do you already use any AI tools in your daily work (ChatGPT, Copilot, SAP's Joule)? What have you learned about when you trust them and when you don't?
  5. 50Are there client-side restrictions we must respect — data that can't leave certain systems, naming that can't appear in a repo, approval needed before adopting a new tool?
N

The first ninety days — building the habit

Goal: adoption is won or lost early. Co-design the rollout with the team so it's theirs, not something imposed.

  1. 51What single use case should the wiki nail first to win you over — legacy code explanations, FAQ answers, decision lookup, onboarding material?Force a ranking; "all of it" is not an answer. This is the most important question in the kit.
  2. 52Would a "seed sprint" be worth it — a week where we deliberately back-ingest the most valuable existing documents — and who could name the top twenty documents to feed it?
  3. 53Who on the team would volunteer to be the curator (quality gatekeeper) and who the intelligence lead (promotes repeated lessons)? Should these rotate?
  4. 54How should we handle the awkward middle period when the wiki is half-empty — is a page saying "the vault doesn't know this yet, ask a named colleague" acceptable, or does that erode trust?
  5. 55What check-in rhythm would you accept to keep it honest — a 20-minute weekly review, monthly, or only when something breaks?
  6. 56How will we know it's working? Pick a signal you'd believe: fewer repeated questions in the team channel, faster onboarding, wiki links appearing in ticket resolutions, people citing pages in meetings?

Only have 30 minutes?

Ask the ten amber-marked questions: 2, 3, 6, 9, 13, 14, 19, 21, 29, 30 — plus 51 if you can squeeze in one more. Together they cover knowledge loss, repeat demand, the legacy-code feature, trust, and adoption — the answers that actually change how the wiki should behave.

Facilitation tips

  • Ask for stories, not preferences. "Tell me about the last time…" beats "would you like…". People are poor predictors of tool usage but accurate reporters of past pain.
  • Anchor Part 2 in last week. For themes J–L, keep pulling answers back to real recent moments. Themes M–N are co-design, so hypotheticals are fine there.
  • Force rankings. Whenever someone answers "all of it", ask them to pick one. Question 51 especially.
  • Close the loop. Write the answers up and drop the document into raw/inbox/ — the interview itself becomes the vault's first stakeholder-signal ingestion, a live demonstration of the system working.

Resources — five kindred builds

Writeups of the same pattern elsewhere, and what each one validates about this project.

  1. 1

    How I Built a Self-Maintaining Knowledge Base for 6 Projects Using Claude Code & Karpathy's LLM Wiki

    HackerNoon

    The closest match in spirit: a practitioner's end-to-end account of a self-maintaining, LLM-curated knowledge base across multiple projects, using git hooks to trigger Claude automatically when content changes — the same "automation reacts to new material" idea as our workflow trigger. (Caveat: the site blocks automated readers, so this was assessed from search metadata rather than a full read.)

  2. 2

    Building an AI-Powered Knowledge Management System: Automating Obsidian with Claude Code and CI/CD Pipelines

    Corti

    Architecturally the nearest neighbor to this repo: an Obsidian vault treated as a code project, with GitHub Actions workflows that validate content (broken wikilinks, missing metadata), run Claude for enhancement (tagging, link suggestions), and deploy on every commit. Verified: moderate-depth tutorial with a complete GitHub Actions workflow config and working script examples — concepts are strong, though some snippets are illustrative rather than production-ready.

  3. 3

    How to Build an LLM Wiki Knowledge Base with Obsidian and Claude Code

    MindStudio

    Verified as a genuine step-by-step tutorial with working code. Covers the full loop: vault setup with a schema file (their equivalent of our CLAUDE.md constitution), extraction scripts for PDFs/YouTube/web pages, an ingestion prompt telling Claude how to process and link content, automation scripts, and — notably — edge-case handling (large PDFs, duplicate detection), which maps directly onto the robustness work in our pipeline.

  4. 4

    Building a Self-Improving Personal Knowledge Base

    Louis Wang

    Verified. The clearest articulation of the design pattern: a raw/ staging layer → Claude-compiled wiki → outputs, with explicit compile, deduplicate-and-merge, and "reflect" steps (synthesis across sources — the equivalent of our pattern-promotion rule). More an architectural essay than a tutorial, but there's a companion GitHub repo. Best read for whoever plays curator.

  5. 5

    How to Send Requests to GitHub API from Power Platform using Custom Connector

    GoToGuy Blog

    Verified, and it's the missing Microsoft-side piece: a thorough walkthrough of connecting Power Automate to GitHub — OAuth app setup, a custom connector with operations to update files and trigger GitHub Actions workflows, plus a ready-made OpenAPI definition. Pair it with a OneDrive "when a file is created" trigger and you have exactly our bridge documented. Older (2021) but the connector approach is still current; Microsoft's docs confirm the same operations exist natively now.

Worth bookmarking beyond the five

  • lucasastorian/llmwiki — open-source Karpathy-pattern implementation: upload documents, Claude writes the wiki.
  • githubnext/awesome-continuous-ai — GitHub's curated list of AI-in-Actions patterns, useful for evolving the pipeline.
  • Automating Markdown uploads to S3 + Bedrock Knowledge Base sync with GitHub Actions (Medium) — if the vault should ever also feed a RAG-style Q&A bot.

How to read them against this project

#2 and #3 validate the GitHub Actions + constitution-file approach; #4 validates the raw-inbox/compile/promote architecture; #5 documents the Power Platform bridge; #1 shows the same idea sustained across multiple projects. Nothing out there has our dedup registry, entity normalization, or the estimation-calibration loop — those appear to be this project's own contributions to the pattern.
